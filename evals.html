Evaluation

How CureCue is evaluated, in eight steps.

Every result here is computed in your browser from the files CI scores on every push. The engine is rule-based and calls no model; the turns are synthetic, written and labelled by one author. Each step says what it does not prove.

Pick a step to see what it does, the numbers it produces today, and what it does not prove. Steps 1 to 7 run in the prototype; step 8 is designed. Open the evaluation console to browse every turn.

Four principles become eight gates. Each gate answers one question a reviewer would ask, and a missed gate fails the build.

What this does not prove
  • The bars are judgement calls, and three were lowered in the same change that added the hard set: escalation recall 1.00 to 0.97, right rule cited 0.95 to 0.92, dissatisfaction 0.90 to 0.88. Escalation precision went up, from 0.80 to 0.85. Release 3 passes the new bars; on today's set it would fail the old escalation bar.
  • "Figures off the cited path" is zero partly because the prototype's drafts are three fixed templates. The check is real and runs on every draft. It starts to mean something once a model writes the drafts.

Each turn is labelled by intent, not by what the rules output. A label is a verdict (answer, person, or escalate), a clause when there is an answer, a dissatisfaction flag, and strata. eval/golden.js is generated by a script that never imports the rules.

What this does not prove
  • One person wrote the turns, the labels and the rules. Release 3's stop patterns were written with the hand and adversarial turns in view, so on those turns the set measures fit. The hard set, written after Release 3's patterns were fixed, is the closest thing to unseen data.
  • The labeller tag (A or B) alternates by row. The -turn two-labeller subset is scripted to show what disagreement looks like. Its agreement of is illustrative, not measured.
  • The prototype has one plan's rules. Plan type is tagged by rotation, so no result is reported by plan.

Before the engine is scored, the data is scored. Two checks run first in CI and stop the build if anything is inconsistent.

The golden set

Unique ids and texts. Every stratum value is in its allowed list. Every answer names a clause, and every clause exists as a node in the rules graph. No non-answer carries a clause. Adjudicated rows carry both labels.

The synthetic book of business

Every claim's member and rule exist. Plan paid plus member owed equals billed. Copays match the rules ($35 specialist, $110 ER, $0 if admitted). No open case is past its clock. Rosa's record matches the scripted call.

What this does not prove
  • These checks catch inconsistency, not wrong judgement. A label that is consistent but wrong passes.

An average hides exactly the members a fairness principle exists for, so every metric is also reported by slice. Counts are shown next to rates because many slices are small.

CI runs the data check and the eval on every push to every branch. A missed gate exits non-zero and fails the build; the runner has no override flag. Older releases stay in rules.js so they can be re-scored on today's set.

What this does not prove
  • In this repository a red build does not stop a deploy: main is not branch-protected and GitHub Pages publishes on its own. In production the eval check would be required before merge and deploy.
  • Releases 1 and 2 failing today is a re-score. In history, Release 1 was blocked on the original set and Release 2 passed it.

What this does not prove
  • Passing every gate is not the same as no misses. The list is the complete set of turns where Release 3 disagrees with a label; it stays on the page until a release fixes each one.

A judge, normally a model scoring answers, may feed a gate only where it agrees with human labels on a held-out slice. Under the threshold it is refused, and the refusal is printed. Escalation is never given to a judge, whatever the agreement.

What this does not prove
  • The prototype's judge is a word-list scorer, not a model. The same author wrote it and the golden set, so its agreement overstates what a real judge would reach.
  • No gate reads the judge today. Every gate is scored against the human labels directly. The table demonstrates the validation mechanism, nothing more.

After launch, the same gates run on real calls. Nothing in this step is built yet.

Shadow first

Cue runs on live calls but no advocate sees a cue. The same metrics, scored against labels from the daily sample.

Daily sample

200 turns relabelled by two advocates. Every grievance or escalation is sampled by rule, and agreement between the two is reported.

Drift by slice

Recall by day, plan, language path and register, with the same gap gate as offline.

Pause rule per topic

A topic under its gate stops drafting and the advocate sees "assist paused". The rest of the product keeps running.

Canary

5% of advocates for three days, against control, on recall, abstention, note omissions and handle time.

Kill switch per skill

An owner stops one behaviour without stopping the product. The pause is itself logged.

What this does not prove
  • Sample sizes, percentages and durations here are starting proposals, to be set from shadow-mode data and agreed with the review board.
