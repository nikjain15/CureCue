From document to rule

How a page in a plan document becomes a rule Cue can cite.

Today's pipeline is small and checked by hand and by CI. The production design keeps the same contract: no rule exists without the exact line and page it came from.

  1. CollectPublic plan PDFs, stored with a checksum and plan year.
  2. ExtractText per page, two reading orders: table rows and wrapped sentences.
  3. ProposeEach rule: what it says, its figures, its exceptions, the quote and the page.
  4. VerifyThe quote must be on that page, or the rule is rejected.
  5. ReviewA person approves each rule and each change from last year.
  6. ServeRules as a graph; the path walked is the citation shown.

Built today

  • Collect: the plan's 2026 Summary of Benefits and Evidence of Coverage, kept in sources/ with SHA-256 checksums (sources).
  • Extract: pdftotext, page by page, in layout and reading order, so a cost-sharing table and a wrapped sentence are both findable.
  • Propose: by hand. 11 rules, each with its plain text, figures and the exact line it was read from (15 quotes).
  • Verify: eval/check-sources.mjs runs on every code change: each PDF matches its checksum and each quote is found on its cited page. A planted wrong figure fails the build.
  • Try it live: in the desk, Connections re-fetches the plan's PDFs, compares their checksums and finds each quote on its page in your browser; Add another plan reads any plan's 2026 Summary of Benefits and compares its rules with the plan on file.
  • Serve: phrase patterns find the entry rule; the walk follows typed edges (unless, then, counts to); every figure in a draft must sit on a rule on that path.

Designed for production

  • Collect every document per plan and plan year (Evidence of Coverage, Summary of Benefits, Annual Notice of Change, formulary, directory) into a versioned store; a new checksum triggers re-extraction.
  • Extract with a layout-aware parser that turns cost-sharing tables into rows (service, setting, cost-share), with OCR as a fallback, keeping page anchors.
  • Propose with a model that must return each rule with its quote and page. Candidates whose quote is not on the page are dropped automatically, by the same check as today.
  • Review by a benefits analyst, starting from the year-over-year diff the Annual Notice of Change describes; test lines tied to a changed rule re-run before release.
  • Reconcile against the plan's benefit configuration in the claims system, the source of truth for what is actually paid; mismatches go to a person.
  • Serve from a graph per plan year; a vector index over sections finds the entry rule, the graph does the rest.
Why not just retrieve chunks of the PDF?

Benefit rules point at each other. The ER copay paragraph does not say what happens after admission; that is in another row, and the yearly maximum is on another page. A chunk answers "$115" and stops. The graph walks ER, then "$0 if admitted", then the daily hospital copay, then the yearly maximum, and shows each page.

What is the honest limit?

Today the rules are entered by hand from one plan, and only 11 of them. The checks are real and run on every change, but model extraction, the year-over-year diff and reconciliation with the claims system are designed, not built.

Safety

Three independent controls stand between Cue and a coverage decision.

No single layer holds, so none is trusted alone.

Type

The verdict has three values: answer, needs a person, escalate. A coverage decision has no type to be emitted as.

Order

Guardian runs before routing on every turn, so a dispute mid-question still wins the race.

Person

The advocate confirms every figure and sends every recap. Human accountability as a design property.

Edge

Designed: identifiers redacted before any model call (the prototype calls none). Member speech is data, never instruction.

Output

A figure not on the cited path fails the build. Tone and reading level are gated for anything member-facing.

Operations

Designed: a kill switch per skill with a named owner. A pause stops one behaviour, not the product.

Questions

What this design gets asked.

Why a graph and not just retrieval over documents?

Benefit rules cross-reference each other with exceptions. A chunk returns the ER paragraph and stops; the graph walks to the admission exception. The path is also the citation a reviewer can read.

How do you know the evals are right?

Labels come from a script that never imports the rules, the data is checked before the engine runs, and results are reported per source so the hard set, written after the rules were fixed, is read apart from the turns the rules were written against. The judge (a stand-in word-list scorer in the prototype) is validated against the labels on a held-out slice and refused where it disagrees; no gate reads it yet.

What stops it giving medical or coverage advice?

The verdict type has no value for a decision, hard-stop topics run before routing, and the advocate confirms every figure. Three layers, independent.

How does it handle protected health information?

Built: the identity gate before any suggestion, and fictional member data only. Designed: redaction at the edge before any model call, member memory read-only, no per-member inference, traces that carry run ids, not identifiers.

Would a real discharge dispute always go to a supervisor?

Not necessarily. What the rules require is in the plan's own documents: the member gets a written notice, and a fast-track appeal goes to the Quality Improvement Organization, which is independent of the plan (Evidence of Coverage, pages 146 to 148). Who inside the plan helps with that call is the plan's own policy. Many plans let the advocate give the appeal rights directly, or warm-transfer to a grievances and appeals team or a care manager. CureCue's stop sends it to "a person with authority"; the demo shows a supervisor because that is the most common escalation path on a service floor. The routing target is configuration, not code.

What happens when the plan year changes?

Designed: the graph is versioned by plan year, and a diff job compares the Annual Notice of Change against last year's nodes and lists exactly which golden rows need relabelling. The prototype has one plan year.

Which model?

The prototype calls none: it proves the rules, gates and evals first. Designed: whatever the enterprise gateway approves, small model for classify and extract, larger for compose. A swap is a config change plus an eval run.

How would you roll it out?

Shadow mode on live calls, 5% canary, promotion on a signed checklist, a pause rule per topic, a kill switch per skill with a named owner.

What is the business case?

Advocate minutes per benefit lookup across a very large call volume, grievances logged that would have been missed, repeat calls avoided because the note was complete. A model with its assumptions visible, never a borrowed figure.

What would you build next?

Coverage clarity for members on the same graph, then network navigation once the directory's freshness problem is solved, then primary care last because it needs a clinical eval first.
