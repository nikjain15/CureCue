CureCue
How it is built, and why · companion to the advocate desktop prototype

CureCue sits beside the advocate, one level deeper than call summaries

A large Medicare Advantage plan runs member service with an assistant in the background and the advocate accountable for every interaction. CureCue keeps that posture and adds the three things a reviewer asks about: when it stops, where its numbers come from, and how it is measured.

Why a graph: benefit rules reference each other, with exceptions

The same question, two retrievals

"If the ER admits me, what do I owe?"

chunk retrieval returns the ER paragraph and stops. Answer: "$110." Confidently wrong for an admitted member.

graph walk ER copay → unless admitted → then hospital copay → counts to yearly max. Answer cites four rules in order, and the path is the citation.

What the graph is

  • Nodes: plan, benefit, clause, rule, exception, process, provider, plan year
  • Edges: requires, exception-to, then-applies, counts-toward, distinct-from, issued-by, in-network-for, supersedes
  • Built from: EOC, ANOC and SOB documents by an extraction pipeline with a human review step, per plan year and county
  • Retrieval: hybrid. A vector index finds the entry node from the member's words; the walk follows typed edges from there, bounded by depth and plan year

Why governance likes it

  • The path is explainable to a reviewer
  • An ANOC changes specific nodes, so the invalidated golden rows can be listed exactly
  • Explainability is met by construction, not by a paragraph

Honest limits, said first

  • Graph construction is the expensive part and needs review
  • Coverage is only as good as the extraction
  • For questions outside the plan (claims status, billing) the graph has nothing and CureCue abstains
  • Graph retrieval is for rule-shaped knowledge, not for everything

Ground truth

Hand-labelled per turn: verdict, clauses on the path, grievance flag, note elements. Written without the engine. Stratified by register, language path, plan type and plan year.

Corpus check first

Test data is scored for internal consistency before the engine runs. Generated data reads as real until someone computes a ratio over it.

Judge, validated or refused

Agreement with people on a held-out slice decides whether a judge may feed a gate (0.85). Refusals are shown on the scorecard. A judge is used only where it has been validated.

Live

Daily 200-turn sample relabelled by two advocates. Recall by day, plan, language. A pause rule stops drafting for a topic that slips, and tells the advocate.

Error budgets and CI

Each metric has a budget and a named owner. The eval runs on every change to a skill or context file. A failed gate fails the build. No override flag exists.

Through the gates, and better every week

Stage gates

The scorecard is generated from a run id and sectioned by four typical published AI principles: Responsible in Application (what CureCue will not do, enforced in code), Fair and Inclusive (recall gaps by language path and plan), Reliable and Safe (hallucination, citation, abstention, live monitoring), Accountable (advocate confirms every figure, two human gates, kill-switch owners). The checklist is generated from the same run. Model card and data lineage attached. A reviewer reads results, not promises.

The loop

  1. Capture every call, cue and click
  2. Label: 200 calls a day re-checked by two advocates
  3. Measure nightly; scorecard rebuilt
  4. Optimizer proposes one change with the calls that motivated it
  5. A person decides
  6. 5% canary, three days, against control
  7. A person signs the generated checklist
  8. Watch; pause a topic that slips

Before every promotion an adversarial audit agent attacks the system with strange phrasings, contradictory EOBs, stale directory entries and code-switched sentences. Every finding becomes a golden row.

Questions this design gets asked

Why a graph and not just RAG?

Benefit rules cross-reference each other with exceptions. A chunk returns the ER paragraph and stops; the graph walks to the admission exception and the inpatient copay. The path is also the citation and the thing a reviewer can read.

How do you know the evals are right?

The expected side is written without the engine and the test data is checked for consistency before the engine runs. The judge is validated against people on a held-out slice and refused where it disagrees. The scorecard is the output of a run, not a document someone wrote.

What stops it from giving medical or coverage advice?

The verdict type has three values and none is a decision. Hard-stop topics run before routing. The advocate confirms every figure. Three independent layers.

How does it handle PHI?

Redacted at the edge before any model call; identity gate before any suggestion; member memory read-only; no per-member inference; traces carry run ids, not identifiers.

What happens when the plan year changes?

The graph is versioned by plan year. The Steward diffs the ANOC against last year's nodes and lists exactly which golden rows are invalidated and which need relabelling. The golden set has an owner.

What is the business case?

Advocate minutes per benefit lookup across a very large call volume, grievances logged that would have been missed (a regulated clock and a Stars input), repeat calls avoided because the note was complete. A model with its assumptions visible, never a borrowed figure.

How would you roll it out?

Shadow mode on live calls with no advocate seeing it; 5% canary; promotion on a signed checklist; pause rule per topic; kill switch per skill with a named owner.

Which model?

Whatever the enterprise gateway approves; skills are model-agnostic. Small model for classify and extract, larger for compose. Routing is a product decision about cost and risk.

How does it get better?

The loop: capture, label, measure, propose, a person decides, canary, a person signs, watch. Nothing changes itself.

What would you build next?

Coverage clarity (same graph, member-facing, reading-level gate), then network navigation (the directory's freshness problem first). Primary care last, because it touches clinical judgment and needs a clinical eval before a single draft exists.

Demonstration material. No real plan, member, provider or document is represented.
